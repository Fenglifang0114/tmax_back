# 电子秤标签打印格式通讯协议指南（设备端解析专用）

本文档专门为单片机、RTOS 等【设备终端固件开发人员】编写。文档详细描述了从上位机（PC端）下发的 **标签打印（Label）** 协议格式结构及解析方式。（*本文暂不包含收银票据 Receipt 格式说明*）

---

## 1. 协议包整体结构 (Packet Structure)

上位机发送的每个标签格式文件均为 `.bin` 二进制格式。其整体物理结构分为三大段：

| 块名称 | 字节数(Bytes) | 说明 |
|---|---|---|
| **头部信息 (Header)** | 468 或 1668 | 描述了格式总数、偏移量以及打印变量（如重量、单价）占位符所在的确切内存相对位置。 |
| **指令载荷区 (Payload)**| 不定长 | 各品牌打印机（如 ZEBRA, TSC, EPM205 等）对应的原生指令数据（例如 TSPL / EPL 字符串），内部会被补齐 4 字节边界对齐。 |
| **结束标识符 (Tail)** | 8 | 固定的 8 字节结束特征码，用于定位包尾截断。 |

---

## 2. 数据封包细节与C语言定义

**重要提示：针对硬件固件解析，全局字节序必须采用 `Little-Endian` (小端序) 进行读写，切记声明结构体时务必使用 `__attribute__((packed))` 或 `#pragma pack(1)` 消除 CPU 缺省边界隐式对齐。**

### 2.1 头部结构定义 (C Language Struct)

#### ① 变量坑位声明 (`VarStruct` - 10 Bytes)
每个变量信息体长 10 字节。该结构主要告知设备固件：应该把哪个字段（重量、总价等）的值填到 Payload 内存中的哪个偏移位。
```c
#pragma pack(1)
struct VarStruct {
    uint16_t id;          // 变量映射ID (以此查询秤内部变量对照表)
    uint16_t startPos;    // 起始替换位置（注：该地址是相对当前当前 Payload 指令首部的内存偏移量）
    uint16_t endPos;      // 写入结束位置 / 占坑位尾端
    uint16_t align;       // 秤端向坑位填数据的排版对齐要求 (0:左, 1:中, 2:右)
    uint16_t maxlen;      // 此坑位能容纳的最大文本字符宽(防止跨区溢出)
};
#pragma pack()
```

#### ② 打印区块索引 (`InfoStr` - 12 Bytes)
如果有多个标签模板或者标签内容被分割，则使用此目录结构导向对应的 Payload 区块。
```c
#pragma pack(1)
struct InfoStr {
    uint32_t addr;        // 当前这套标签Payload命令区的首字节绝对地址（相对于完整包起始位置）
    uint32_t formatLen;   // 当前这套标签Payload命令区域所占的物理字节总长
    uint32_t varNum;      // 归属于此标签区的有效变量元素(VarStruct)总数量
};
#pragma pack()
```

#### ③ 完整的包头主干 (Header)
根据具体下发的标签量级场景，表头结构有两种。普通秤应用最广泛的是单张发配使用的 **468字节** 头结构。

**结构A：常规单张标签封包 (定长 468 Bytes)**
```c
#pragma pack(1)
struct printInfo {
    uint8_t  printerName[23];  // 打印机识别码。前22字节为品牌名称，第23个字节 0x00 表示 Label
    uint8_t  formatNum;        // 附带的有效打印模板格式块总数
    struct InfoStr everyFormatInfo[12]; // 144 字节
    struct VarStruct varInfo[30];       // 300 字节，按顺序存放变量索引
};
#pragma pack()
```

## 3. 变量传输与动态识别机制 (Variable Handling)

本协议的核心设计思想是：**“上位机挖坑，下位机填土”**。上位机（PC）在生成二进制指令载荷时，预留出变量位置，并通过文件头的 `VarStruct` 告知硬件固件如何准确地将实时数据映射进去。

### 3.1 变量识别流程 (Identification Flow)

1.  **PC端定义**：上位机维护一份变量映射表，将语义化的变量名映射为唯一的**数值 ID**。
2.  **指令占位**：PC端解析模板时，遇到 `DATA` 字段会生成一段带空字符串的指令。例如：`A10,10,0,3,1,1,N,""`。
3.  **元数据下发**：PC计算出引号内部在 `Payload` 中的起始字节偏移量（`startPos`），连同变量 `id`、长度 `maxlen` 等封装进 `VarStruct`。
4.  **下位机执行**：秤端固件读取数据后，根据 `id` 获取传感器实时数值，转换为字符串，根据 `startPos` 强制覆盖 Payload 对应内存区域。

### 3.2 变量 ID 映射与分拆机制 (ID Mapping & Splitting)

上位机在下发时，会将某些复合变量分拆为多个独立的 `VarStruct` 条目。**设备端必须能识别这些细分 ID**：

#### A. 日期与时间分拆 (RTC Components)
当上位机配置 “Date” (ID 1) 或 “Time” (ID 2) 时，生成的二进制包头中会包含如下映射（**PC会自动在 Payload 中预填 `/` 或 `:` 分隔符**）：

| 二进制 ID | 语义 | 默认长度 (maxlen) | 示例 |
|:---:|---|:---:|---|
| **1** | 年份 (Year) | 4 | 2024 |
| **2** | 月份 (Month) | 2 | 04 |
| **3** | 日期 (Day) | 2 | 15 |
| **4** | 小时 (Hour) | 2 | 13 |
| **5** | 分钟 (Minute) | 2 | 45 |
| **6** | 秒钟 (Second) | 2 | 01 |

> **开发注意**：分隔符（如 `2024/04/15` 中的 `/`）是由上位机预先写死在 Payload 字符串里的，下位机**只需**根据 `startPos` 寻找对应的位置覆盖纯数字即可，千万不要自己去改动分隔符，否则会破坏排版长度。

#### B. 常用业务数据 (Business Data)
| ID (Dec) | 变量名称 | 说明 |
|:---:|---|---|
| **8** | `Gross` | 毛重 (Gross Weight) |
| **9** | `Tare` | 皮重 (Tare Weight) |
| **10** | `Net` | 净重 (Net Weight) |
| **11** | `PCS` | 计数个数 |
| **12** | `UnitWeight` | 单重 |
| **38** | `PLU_Name_P` | 商品名称 (从秤端 PLU 库调取) |
| **40** | `UnitPrice_P` | 商品单价 |
| **42** | `Price_P` | 总计价格 (Net * UnitPrice) |
| **254** | `StartLoop` | 循环体起始 (用于标识动态明细行) |

### 3.3 VarStruct 关键字段深度解析

*   **`id`**: 核心识别码。固件读取此值决定从秤内部哪个寄存器（重量、单价、RTC）取数。
*   **`startPos`**: **绝对偏移量**。固件定位地址 = `Payload_Buffer_Start + startPos`。
*   **`maxlen`**: **安全阈值**。填土时严禁超过此长度。例如年份 maxlen=4，即使是 202411 也要截断为 2024。
*   **`align`**: **排版风格**。
    *   `0 (Left)`: 数据靠左，右侧用空格 `0x20` 补齐至 `maxlen`。
    *   `1 (Center)`: 居中对齐，左右对称补空格。
    *   `2 (Right)`: 数据靠右，左侧用空格补齐。

## 4. 载荷区打印指令 (Payload) 转换说明

*   **多语言编码**：所有指令中的汉字内容均已提前转换为 **GB2312 编码**。
*   **硬件兼容前缀**：部分机型（如EPM205）可能在 Payload 开始位置包含跳码指令：`1F 28 4C 03 00 43 45 06`。
*   **4字节整倍对齐**：为方便 32 位处理器内存操作，Payload 段末尾会以 `0xFF` 填充至 4 字节边界。

## 5. 结尾特征标识 (Tail End / EOF)

上位机在物理文件末尾追加 **8字节定长** 的结束标识，用于设备端接收流判定：
```c
// EOF序列 (Hex): 5A A5 A5 5A 00 00 00 00
```

## 6. 秤端固件开发作业 SOP

1.  **解析表头**：获取 `printerName` 判定协议类型，读取 `formatNum`。
2.  **准备内存**：根据表头中的 `addr` 和 `formatLen`，将原始 Payload 指令拷贝至可读写的缓冲区。
3.  **动态覆写变量**：
    *   遍历 `varInfo` 数组。
    *   根据其 `id` 获取秤内部最新的实时数据（如 `Net` 重量）。
    *   将数值转为字符串，并根据 `align` 补齐至 `maxlen`。
    *   **关键动作**：将处理好的字符串写入 `Payload_Buffer + startPos` 位置，覆盖原有的空位。
4.  **下发打印**：将最终“填好土”的缓冲区发送至打印头。

### 3.4 复合指令中的变量 (Variables in Barcodes/QR Codes)

变量不仅可以存在于 `TEXT` 指令中，也可以嵌入在条码（Barcode）或二维码（QR Code）的内容里。

*   **机制一致性**：无论载荷指令是 `TEXT`、`BARCODE` 还是 `QRCODE`，其内部的变量处理逻辑是完全一致的。
*   **定位方式**：`startPos` 会直接指向条码指令数据区的引号内部。
    *   *示例*：EPL 指令 `B10,10,0,1,2,2,50,B,"123456"`。如果 `123456` 是重量变量，则 `startPos` 会指向 `1` 的位置。
*   **开发建议**：秤端固件在执行变量覆写时，无需关心该位置属于什么指令类型，只需按字节偏移量进行覆盖即可。

---
> 综上所述，该协议通过**静态描述 + 动态覆盖**的机制，确保了高排版灵活性与低实时响应延迟。
